An API key leaked into your agent's log. Now what?

Agents print a lot: environment dumps, failing curl commands, config files they just read. Sooner or later a key ends up in a run log, a chat transcript, a screenshot or a commit. This is the order of steps that limits the damage. Speed matters more than perfection in the first minutes.

The short version

  1. Revoke the key at the provider. Do this first, before cleaning anything.
  2. Create a new key and update it where your agent reads secrets.
  3. Check usage on the provider dashboard for calls you didn't make.
  4. Find every copy (logs, transcripts, commits, tickets) and remove or redact it.
  5. Fix the cause so the agent can't print it again.

1. Revoke first, clean up second

Deleting the log line does not un-leak the key. Anyone or anything that already read the log (a sync job, a backup, a hosted chat history, a public repo mirror) still has it. Treat the key as burned the moment it was written somewhere you don't fully control, and revoke it in the provider's dashboard. Most providers list keys under account or project settings, usually in a section called "API keys" or "Tokens". For GitHub tokens it is Settings → Developer settings; for AWS access keys it is the IAM user's security credentials.

2. Rotate and update the agent's secret store

Create a replacement key with the smallest scope that still works: read-only if the job only reads, one project instead of the whole account, an expiry date if the provider offers one. Put it into the place your agent actually loads secrets from (a secrets manager, an env file outside the repo) and run the job once to confirm it still works. A rotated key nobody tested is how the 3 a.m. cron run fails.

3. Look for usage you didn't cause

Open the provider's usage or billing page and compare the time window between the leak and the revoke. Unusual spikes, unknown models, other regions or calls at odd hours are the signs to look for. If you see abuse, contact the provider's support with the key ID (never the key itself) and the time window. Also set a spending limit or budget alert if the account has none.

4. Find every copy

Agent setups usually keep more copies than you think:

  • daily run logs and their rotated or archived versions,
  • chat or session transcripts the agent framework stores,
  • git history: a later commit that deletes the line does not remove it from earlier commits,
  • CI logs, issue comments, pasted error messages, screenshots.

Paste a suspicious log into the Agent Log Secret Scanner. It runs entirely in your browser, flags common key formats (Anthropic, OpenAI, GitHub, AWS, bearer headers, passwords in URLs, private keys) and gives you a redacted copy. Since the key is already revoked, redaction here is about hygiene and not leaving bait in old files.

5. Fix why it got printed

  • Never pass secrets as command-line arguments or inline in commands the agent echoes. Read them from env or a secrets CLI inside the script, so the transcript shows the variable name, not the value.
  • Don't let the agent print whole API responses or config objects. Some APIs return a key field in their account or settings endpoints. Filter to the fields you need.
  • Mask in logs. Pipe tool output through a redaction step before it is written to disk.
  • Block it at the repo. Enable secret scanning or push protection where your git host offers it, and add a pre-commit check.
  • Scan regularly. A daily leak check over the newest logs costs nothing and catches the next one early.
